## 1. 共通の評価観点（チェックリスト）
| 観点 | チェック内容 | 意図 |
| :--- | :--- | :--- |
| **正常系の定義** | 期待されるゴールは何か？画面遷移やDBの状態はどう変わるか？ | 手戻りを防ぐ |
| **異常系の定義** | 未入力、不正な値、DB接続エラー時にどう振る舞うべきか？ | システムの堅牢性 |
| **UI/UXの整合性** | 操作後に「何が起きたか」ユーザーが理解できるか？（メッセージ表示等） | 利用者のストレス軽減 |
| **セキュリティ** | 権限のないユーザーがURL直打ちで操作できないか？ | 信頼性の確保 |
| **データ整合性** | 同時実行（ダブルクリック等）でデータが壊れないか？ | DBの信頼性 |

## 2. 初級（Beginner）仕様と実装手順

### 【管理者を登録する】

#### (1-1)初級 画面遷移
1. **決定した仕様（正解）**: 
   - 登録完了後、ログイン画面へリダイレクト（PRGパターンの適用）。
   - 実務的なUI/UXを考慮し、ログイン画面に「登録が完了しました。ログインしてください。」等のフラッシュメッセージを表示する。
2. **講師への確認ポイント**: 
   - 「登録完了後、ただログイン画面を表示するだけでなく、『登録が完了しました』というメッセージを出した方がユーザーにとって親切だと考えますが、よろしいでしょうか？」
3. **ロジック・手法**:
   - `RedirectAttributes.addFlashAttribute("infoMessage", "登録が完了しました。");` を設定。
   - 戻り値を `return "redirect:/";` とする（フォワードやそのままの画面表示はNG）。
4. **正常/異常系定義**:
   - 【正常系】DBにインサートされ、ログイン画面にリダイレクトし、完了メッセージが表示される。
5. **JUnitテスト観点**:
   - `MockMvc` を使用し、リクエスト結果のステータスコードが `302 (Redirection)` であること、リダイレクト先が `/` であること、Flash属性に期待するメッセージが含まれていることをテストさせる。

#### (1-2)初級 入力値エラー処理
1. **決定した仕様（正解）**: 
   - エラー発生時は画面遷移（リダイレクト）せず、元の登録画面をフォワードで返し、エラー内容を画面に表示する。フォームの入力値は保持される。
   - DBは無制限（text型）だが、システム運用やDoS攻撃防止の観点から以下のバリデーション境界を設ける。
     - **名前**: 必須入力 (`@NotBlank`)、最大50文字 (`@Size(max = 50)`)
     - **メールアドレス**: 必須入力 (`@NotBlank`)、形式チェック (`@Email`)、最大254文字 (`@Size(max = 254)`)
     - **パスワード**: 必須入力 (`@NotBlank`)、8〜16文字 (`@Size(min = 8, max = 16)`)
2. **講師への確認ポイント**: 
   - 「DBの定義は text 型で文字数制限がありませんでしたが、システム運用上のリスク回避のため、名前は最大50文字、メールは最大254文字、パスワードは8文字以上16文字以内といった制限を加えてもよろしいでしょうか？」
3. **ロジック・手法**:
   - `Form` クラスに `@NotBlank`, `@Email`, `@Size` を付与。
   - `Controller` の引数に `@Validated` と `BindingResult` を追加し、エラー時に元の入力画面を返す。
   - Thymeleaf側に `th:errors` と `th:errorclass` を設置。
4. **正常/異常系定義**:
   - 【正常系】全項目正しい値（境界値内）で登録完了。
   - 【異常系】未入力、文字数超過・不足、メール形式違反時に画面遷移せず、元の入力値とエラーメッセージが表示される。
5. **JUnitテスト観点**:
   - `MockMvc` を使用し、境界値（パスワード7文字、17文字など）でインサート処理が呼ばれないことをテストさせる。

#### (1-4)初級 ダブルサブミット対策
1. **決定した仕様（正解）**: 
   - **バックエンド**: 登録完了後の画面遷移を `redirect:` とし、ブラウザの更新ボタンによる再送信を防ぐ（PRGパターン）。
   - **フロントエンド**: マウスのダブルクリックによる連続送信を防ぐため、フォーム送信時（`onsubmit`）に登録ボタンを非活性化（`disabled`）する。
2. **講師への確認ポイント**: 
   - 「更新による二重送信はリダイレクトで防ぎますが、マウスのダブルクリックも防ぐために、ボタンを押した瞬間に非活性化させる機能も入れたいのですが、よろしいでしょうか？」
3. **ロジック・手法**:
   - `insert.html` の `<form>` タグに `onsubmit="document.getElementById('registerBtn').disabled=true;"` を追加。
   - 登録ボタンに `id="registerBtn"` を付与。
4. **正常/異常系定義**:
   - 【正常系】ボタンを1回クリックすると登録処理が走り、ボタンが押せなくなる。
   - 【異常系】意図的に素早く2回クリックしても、JavaScriptでブロックされリクエストが1回しか飛ばない。
5. **JUnitテスト観点**:
   - フロントエンドの制御はJUnit外であることを理解させ、バックエンドのリダイレクトを `MockMvc` で検証させる。

### 【従業員情報を表示する】

#### (3-1)初級 従業員一覧の並び順
1. **決定した仕様（正解）**: 
   - 最近入社した従業員が一番上に表示されるよう「入社日の降順（新しい順）」で並び替える。
2. **講師への確認ポイント**: 
   - 「一覧の並び順ですが、使いやすさを考慮して最近入社した人が一番上に来るよう『入社日の降順』で並べたいと思いますがよろしいでしょうか？」
3. **ロジック・手法**:
   - `EmployeeRepository` の `findAll` メソッドのSQL末尾に `ORDER BY hire_date DESC` を追加する。
4. **正常/異常系定義**:
   - 【正常系】入社日の新しい順に一覧が表示される。
5. **JUnitテスト観点**:
   - 結合テスト等で、期待した順番通りにリストが取得できることを確認する。

#### (4-1)初級 日付フォーマット
1. **決定した仕様（正解）**: 
   - 入社日を `yyyy年MM月dd日` 形式で表示する。一覧画面と詳細画面の両方に適用する。
2. **講師への確認ポイント**: 
   - 「日付は『2015年05月01日』のように表示形式を統一します」
3. **ロジック・手法**:
   - Thymeleafのユーティリティ関数 `#dates.format()` を使用。
4. **正常/異常系定義**:
   - 【正常系】指定されたフォーマットで表示される。
5. **JUnitテスト観点**:
   - プレゼンテーション層の責務であるため、UIテストや画面確認の対象であることを教える。

#### (4-2)初級 価格フォーマット
1. **決定した仕様（正解）**: 
   - 給料を3桁のカンマ区切りにし、末尾に「円」をつける（例：`233,800円`）。
2. **講師への確認ポイント**: 
   - 「給料は『233,800円』のように表示形式を統一します」
3. **ロジック・手法**:
   - Thymeleafの数値フォーマット機能 `#numbers.formatInteger()` を使用。
4. **正常/異常系定義**:
   - 【正常系】カンマ区切りで表示される。

## 3. 中級（Intermediate）仕様と実装手順

### 【管理者を登録する】

#### (1-3)中級 Eメール重複チェック
1. **決定した仕様（正解）**: 
   - 既に登録されているメールアドレスを入力した場合、エラーメッセージ「そのメールアドレスはすでに登録されています」を表示する。
2. **講師への確認ポイント**: 
   - 「メールアドレスが重複していた場合、登録画面に具体的なエラーメッセージを表示する仕様でよろしいでしょうか？」
3. **ロジック・手法**:
   - `AdministratorService.findByMailAddress()` を呼び出し、結果が `null` でない場合に `BindingResult.rejectValue()` を使用してカスタムエラーを登録する。
4. **正常/異常系定義**:
   - 【異常系】登録済みのメールアドレスでエラーメッセージが表示され、登録されない。
5. **JUnitテスト観点**:
   - `MockMvc` を使用し、Serviceが値を返す場合にエラーが含まれることを検証させる。

#### (1-5)中級 確認用パスワード
1. **決定した仕様（正解）**: 
   - パスワード入力欄に加えて「確認用パスワード」欄を設け、両者が一致しない場合はエラー「パスワードが一致しません」を表示する。
2. **講師への確認ポイント**: 
   - 「パスワードの入力ミス防止のため確認用パスワード欄を追加します。不一致時のメッセージ指定はありますか？」
3. **ロジック・手法**:
   - `Form` に `passwordConfirm` を追加。Controllerで比較し、不一致なら `result.rejectValue()`。
4. **正常/異常系定義**:
   - 【異常系】不一致の場合、エラーメッセージが表示され登録されない。

### 【従業員管理全般】

#### (2-1)中級 ログイン者名表示
1. **決定した仕様（正解）**: 
   - ログイン後、全画面のヘッダーに「〇〇さん こんにちは！」と表示する。名前はセッション（`HttpSession`）から取得。
2. **共通化**: 
   - 今後のメンテナンス性を考慮し、ヘッダー部分を `common/header.html` として共通部品化（Thymeleaf Fragment）する。
3. **ロジック・手法**:
   - ログイン成功時に `session.setAttribute("administratorName", administrator.getName())` を行う。
   - 各画面から `th:replace` で共通ヘッダーを呼び出す。
4. **正常/異常系定義**:
   - 【正常系】ログイン後、どの画面に遷移しても自分の名前が表示される。

#### (4-3)中級 パンくずリスト修正
1. **決定した仕様（正解）**: 
   - 詳細画面のパンくずリストから一覧画面へ戻るリンクを正しく設定（`/employee/showList`）。
2. **ロジック・手法**:
   - `th:href="@{/employee/showList}"` を使用し、環境に依存しない動的なパス生成を行う。

#### (6-2)中級 従業員曖昧検索
1. **決定した仕様（正解）**: 
   - 名前の一部で曖昧検索。該当者がいない場合は「１件もありませんでした」と表示しつつ、全件を表示。
2. **ロジック・手法**:
   - SQLの `LIKE :name` 演算子を使用（引数を `%` で囲む）。
   - Controllerでリストの `isEmpty()` を判定し、フォールバック処理を実装。

### 【セキュリティとエラー処理】

#### (5-1)中級 SQL Injection 対策
1. **決定した仕様（正解）**: 
   - 文字列連結によるSQL組み立てを廃止し、プレースホルダ（バインド変数）を使用。
2. **ロジック・手法**:
   - `NamedParameterJdbcTemplate` の `:param` 記法を使用し、`MapSqlParameterSource` で値を渡す。

#### (5-2)中級 XSS 対策
1. **決定した仕様（正解）**: 
   - HTMLエスケープなしの出力（`th:utext`）を廃止し、自動エスケープ（`th:text`）に統一。
2. **ロジック・手法**:
   - 全テンプレートの `th:utext` を `th:text` に書き換え。

#### (6-1)中級 実務的エラー処理
1. **決定した仕様（正解）**: 
   - デフォルトのエラー画面を卒業し、404/500用のカスタム画面を表示。
2. **ロジック・手法**:
   - `templates/error/` 配下にステータスコード名のHTMLを配置（Spring Bootの規約）。

## 4. 上級（Advanced）・超上級（Expert）仕様と実装手順

### 【セキュリティの完成】

#### (5-3)上級 パスワード暗号化 (Spring Security)
1. **決定した仕様（正解）**: 
   - パスワードを DB に保存する際、平文ではなくハッシュ化（BCrypt）して保存する。照合も同様。
2. **ロジック・手法**:
   - `BCryptPasswordEncoder` を使用。Serviceでの登録時に `encode`、ログイン時に `matches` を実行。

#### (5-4)超上級 ログイン認証フィルター (Spring Security)
1. **決定した仕様（正解）**: 
   - 未ログイン状態での直接アクセスを禁止し、門番が一括でログイン画面へリダイレクトさせる。
2. **ロジック・手法**:
   - **完全なDB連携**: `UserDetailsService` を実装し、門番（Security）に DB を読みに行く方法を教える。
   - **項目の紐付け**: `usernameParameter("mailAddress")` 等で HTML 項目と Security 内部項目を紐付ける。
   - **アクセス制御**: `SecurityFilterChain` でパスごとの認可（permitAll / authenticated）を設定。

### 【高度な機能追加】

#### (6-3)上級 従業員登録（完全版）
1. **決定した仕様（正解）**: 
   - 画像アップロード（jpg/pngのみ）、住所自動補完（AjaxZip3）、`synchronized` による ID 自前採番。
2. **ロジック・手法**:
   - **排他制御**: 複数人同時登録での ID 重複を防ぐため、Serviceメソッドに `synchronized` を付与。
   - **画像**: `MultipartFile` で受け取り、`Files.write` でサーバー内フォルダへ保存。

#### (6-4)上級 オートコンプリート
1. **決定した仕様（正解）**: 
   - 検索窓に候補を出す。「datalist方式」または「jQuery UI方式」を選択可能にする。
2. **ロジック・手法**:
   - Controllerから全従業員名リストを Model に詰めて渡し、HTML側で各タグ/JSを実装。

#### (6-5)上級 ページング
1. **決定した仕様（正解）**: 
   - 1ページ10名ずつの小分け表示。ページ番号リンクで切り替え。
2. **ロジック・手法**:
   - SQL の `LIMIT 10 OFFSET :offset` を使用。`(page-1)*10` の計算ロジックを Service に実装。
