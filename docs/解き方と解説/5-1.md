# (5-1) 中級 SQL Injection 徹底解説

> **合格ライン**: 判定は [02_レビュー判定基準.md](../02_レビュー判定基準.md) の **(5-1)** / 別解は [03_別解・許容一覧.md](../03_別解・許容一覧.md) を参照。

## 1. 研修生のスタート地点（バグの状態）
研修生は、既存のログイン処理コードを見て以下のように考えます。
> 「メールアドレスとパスワードを文字列で繋いで SQL を作っているな。普通にログインできるし、特に問題なさそうだけど……。なぜこれが『脆弱性』って言われるんだろう？」

**ここで、ボス（指導者）は「ハッカーの視点」を教えます。**

## 2. 指導者からの「気づき」の問いかけ
研修生に以下のように問いかけてみてください。
> 「もし、悪意のあるユーザーがパスワード欄に `' OR '1'='1` と入力したらどうなるかな？ そのまま SQL に繋げると、どんな命令が出来上がるか想像してごらん。……パスワードが分からなくてもログインできちゃうんじゃない？」

研修生に、**「ユーザーの入力によって SQL の『意味』が書き換えられてしまう」**という恐怖を実感させます。

## 3. ロジックの組み立て方：命令とデータの分離
「SQL という『命令』の中に、ユーザーの入力という『データ』をそのまま混ぜちゃダメなんだ。データを『ただの文字』として安全に扱うための特別な書き方を使おう」と導きます。

1.  **文字列連結を禁止する**: `+ mailAddress +` のような書き方をやめる。
2.  **プレースホルダを使う**: SQL 内では `:mailAddress` のように「穴」を空けておく。
3.  **後から流し込む**: フレームワーク（NamedParameterJdbcTemplate）に、その「穴」に値を安全に入れてもらう。

## 4. メソッド・文法の駆使（実際のコード）

### Repositoryクラスの修正（MiddleAdministratorRepository.java）
```java
public Administrator findByMailAddressAndPassword(String mailAddress, String password) {
    // 修正前（危険！）
    // String sql = "select ... where mail_address= '" + mailAddress + "' and password='" + password + "'";

    // 正解の修正（安全！）
    String sql = "select id, name, mail_address, password from administrators "
               + "where mail_address = :mailAddress and password = :password";

    // 「穴」に入れる値をセットする
    SqlParameterSource param = new MapSqlParameterSource()
            .addValue("mailAddress", mailAddress)
            .addValue("password", password);
    
    List<Administrator> administratorList = template.query(sql, param, ADMINISTRATOR_ROW_MAPPER);
    // ...
}
```

- **文法解説（プレースホルダ）**:
    - `:mailAddress` のように `:` から始まる名前を「名前付きパラメータ」と呼びます。
    - **`MapSqlParameterSource`**: どの名前にどの値を割り当てるかを管理する地図のようなオブジェクトです。
    - これを使うことで、入力値の中に `'`（シングルクォート）が含まれていても、フレームワークが「これは単なる文字データだ」と無害化（エスケープ）して処理してくれます。

## 5. 研修生へのステップアップ課題
「SQLインジェクションでログインを突破されるだけじゃなく、もし `'; DROP TABLE users; --` みたいな文字列を送り込まれたらどうなると思う？」

と問いかけ、データの盗難だけでなく「DBの破壊」すら可能になってしまうリスクの大きさを伝えます。

## 6. まとめ：研修生に伝えたいメッセージ
> 「プログラムを作ることは、扉を作ることと同じだよ。鍵（認証）をかけるだけじゃなく、扉そのものを壊されないように『頑丈な素材（プレースホルダ）』を使おう。セキュリティは、後回しにできないプロの最低限のマナーなんだ。」

## 変更箇所の差分（修正前 → 修正後）

### `AdministratorRepository.java` — ログイン用 SQL（脆弱箇所）

**修正前**（SQL インジェクションの温床）

```java
public Administrator findByMailAddressAndPassword(String mailAddress, String password) {
    String sql = "select ... where mail_address= '" + mailAddress
            + "' and password='" + password + "'";
    SqlParameterSource param = new MapSqlParameterSource();
    return template.query(sql, param, ADMINISTRATOR_ROW_MAPPER).get(0);
}
```

**修正後**

- 上記メソッドは **削除**（または未使用に）。
- ログインは **Spring Security** + `UserDetailsService` が DB からユーザーを取得。
- 他の検索はプレースホルダを使用：

```java
String sql = "select id,name,mail_address,password from administrators where mail_address=:mailAddress";
SqlParameterSource param = new MapSqlParameterSource().addValue("mailAddress", mailAddress);
```

## 7. 付録：コード1行ずつ解説

### 7.1 名前付きパラメータ SQL

```java
String sql = "SELECT ... FROM employees WHERE id = :id";
SqlParameterSource param = new MapSqlParameterSource().addValue("id", id);
return template.query(sql, param, EMPLOYEE_ROW_MAPPER);
```

| 行 | 意味 |
|----|------|
| `:id` | 名前付きプレースホルダ |
| `addValue("id", id)` | **キー名** が SQL の `:id` と一致すること |
| 文字列連結 `"WHERE id=" + id` | SQL インジェクションの危険。本研修では禁止 |
