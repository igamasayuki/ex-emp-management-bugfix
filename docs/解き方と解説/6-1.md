# (6-1) 中級 実務的エラー処理 徹底解説

## 1. 研修生のスタート地点（バグの状態）
研修生は、存在しないURLにアクセスした際に出る「Whitelabel Error Page」を見て以下のように考えます。
> 「英語で何か書いてあるけど、とりあえずエラーだってことは伝わるし、そのままでもいいのかな？ これを直すには、Controller でいちいち 404 エラーを捕まえて画面を返す処理を書かなきゃいけないの？」

**ここで、ボス（指導者）は「プロの製品クオリティ」と「フレームワークの規約」を教えます。**

## 2. 指導者からの「気づき」の問いかけ
研修生に以下のように問いかけてみてください。
> 「もし君が使っている有名なWebサービスで、突然『Whitelabel Error Page』なんて無機質な画面が出たらどう思う？ 『あ、このサイト壊れてる。怖いな』って思っちゃわないかな？ エラーが起きた時こそ、ユーザーを安心させて、次の行動（ホームに戻るボタンなど）を促してあげるのがプロの優しさ（UX）じゃないかな？」

研修生に、エラー画面も「製品の一部」であるという意識を持たせます。

## 3. ロジックの組み立て方：設定より規約（CoC）
「コードを一行も書かずに、ファイルを置くだけでエラー画面をカスタマイズできる便利なルールが Spring Boot にはあるんだよ」と導きます。

1.  **専用のフォルダを作る**: `templates` の中に `error` というフォルダを作る。
2.  **ステータスコードをファイル名にする**: `404.html` や `500.html` を作る。
3.  **メッセージを書く**: ユーザーが次に何をすべきか（ログインへ戻る、など）を明記する。

## 4. メソッド・文法の駆使（実際のコード）

### フォルダ構成
```text
src/main/resources/templates/
  └── error/
      ├── 404.html  (ページが見つからない時用)
      └── 500.html  (サーバー内部でエラーが起きた時用)
```

### HTMLの実装（404.html の例）
```html
<div class="jumbotron">
    <h1>404</h1>
    <h2>ページが見つかりません</h2>
    <p>お探しのページは削除されたか、URLが間違っている可能性があります。</p>
    <a th:href="@{/}" class="btn btn-primary">トップ画面へ戻る</a>
</div>
```

- **文法解説（Spring Boot の規約）**:
    - `templates/error/` 配下にステータスコード名のHTMLを置くと、Spring Boot はエラー発生時に自動的にそのファイルを探して表示してくれます。
    - **404**: Not Found。URLの間違いなど。
    - **500**: Internal Server Error。プログラムのバグやDB接続切れなど。
    - これを **「設定より規約（Convention over Configuration）」** と呼び、Javaの面倒な設定を省ける魔法のような仕組みであることを伝えます。

## 5. 研修生へのステップアップ課題
「もし 400番台（ユーザー側のミス）のエラー全部に対して同じ画面を出したい場合は、どうすればいいかな？ 401.html, 403.html...と全部作る必要がある？」

と問いかけ、`4xx.html` や `5xx.html` というワイルドカード形式のファイル名についても調べさせます。

## 7. 💡 別解：Enum（列挙型）を活用したプロの設計
「登録が完了しました」や「ログインに失敗しました」といったシステムメッセージを、各 Controller に直接書く（ハードコーディングする）のはやめましょう。大規模開発では **Enum** でメッセージを一括管理するのが定石です。

### Enum によるメッセージ管理の定義
```java
public enum SystemMessage {
    REGISTER_SUCCESS("infoMessage", "登録が完了しました。"),
    MAIL_DUPLICATE("errorMessage", "そのメールアドレスはすでに登録されています。"),
    LOGIN_FAILED("errorMessage", "メールアドレスまたはパスワードが不正です。");

    private final String key;   // ModelやFlashに詰める時の名前
    private final String text;  // 表示する文言
    // コンストラクタとGetter
}
```

### この設計が優れている理由：
1.  **表記揺れの防止**: Aさんは「登録完了」、Bさんは「保存しました」と書くような、メッセージのバラツキを根絶できます。
2.  **一括変更の容易さ**: 文言を修正したいとき、全 Controller を探す必要はありません。Enum の定義を一箇所直すだけで、システム全体の文言が更新されます。
3.  **マジックストリングの排除**: 誤字脱字による「メッセージが出ない」というバグを、コンパイラがチェックしてくれるようになります。
