# (5-4) 超上級 ログイン認証フィルター 徹底解説

> **合格ライン**: 判定は [02_レビュー判定基準.md](../02_レビュー判定基準.md) の **(5-4)** / 別解は [03_別解・許容一覧.md](../03_別解・許容一覧.md) を参照。

## 1. 研修生のスタート地点（バグの状態）
研修生は、(2-1) でログイン名を表示できたことで満足していますが、プロの現場では許されない大きな欠陥に気づきます。
> 「ログインしないと一覧画面には行けないはずなのに、ブラウザのアドレスバーに直接 `/employee/showList` って打ち込んだら、中身が見えちゃった……。全てのメソッドの先頭で『セッションに名前が入ってるか？』をチェックする if 文を書かなきゃいけないのかな？」

**ここで、ボス（指導者）は「横断的な関心事」と「一元管理」の哲学を教えます。**

## 2. 指導者からの「気づき」の問いかけ
研修生に以下のように問いかけてみてください。
> 「全ての部屋（URL）の入り口で、いちいち『身分証見せて』とチェックする if 文を書くのは非効率だし、一箇所でも忘れたらセキュリティホールになるよね。建物の正面玄関に最強の門番を一人立たせて、許可証がない人を一括で追い返してくれる仕組みがあったら、中の住人（Controller）は安心して自分の仕事に集中できると思わない？」

## 3. ロジックの組み立て方：門番と名簿の連携
「門番を立たせるだけではダメだ。彼に『正しい社員名簿』を渡し、『名札の読み方』も教えなきゃいけない」という流れで、Spring Security の全容を伝えます。

1.  **門番の教育（UserDetailsService）**: 門番に「DBのこのテーブルを、このRepositoryを使って読みに行ってね」という手順を教え込む。
2.  **項目の紐付け（Parameter Mapping）**: HTML側の「mailAddress」という項目が、門番の言うところの「username」であると翻訳してあげる。
3.  **エリアの指定（URL Authorization）**: どのパスを自由開放し、どのパスに鍵をかけるかを明確に命じる。

## 4. メソッド・文法の駆使（実際のコード）

### 名簿担当者の任命（LoginAdministratorDetailsService.java）
```java
@Service
public class LoginAdministratorDetailsService implements UserDetailsService {
    @Override
    public UserDetails loadUserByUsername(String mailAddress) {
        // 門番の代わりに、自分が DB へ探しに行く
        Administrator admin = repository.findByMailAddress(mailAddress);
        // 見つけた情報を、門番が理解できる「UserDetails」という形式に変換して渡す
        return new User(admin.getMailAddress(), admin.getPassword(), ...);
    }
}
```

### 門番への詳細指示（WebSecurityConfig.java）
```java
.formLogin(login -> login
    .loginPage("/") 
    .loginProcessingUrl("/login")
    // HTML側の項目名（mailAddress）を教えてあげる
    .usernameParameter("mailAddress")
    .passwordParameter("password")
    .defaultSuccessUrl("/employee/showList", true)
)
```

## 5. 💡 ワンランク上のエンジニアリング・トーク
### 「なぜ Spring Security はこんなに複雑なの？」
研修生は、`UserDetailsService` や `UserDetails` といった登場人物の多さに戸惑うはずです。そこでこう伝えてください。

> 「Spring Security は、どんな DB 構造でも、どんな認証方式（指紋認証、SNSログインなど）でも対応できるように作られている『究極の汎用ツール』なんだ。
> 複雑に見えるのは、**『セキュリティの仕組み（門番）』と『データの持ち方（名簿）』を完全に切り離して（疎結合にして）設計されているから**だよ。
> 門番は DB の中身を直接知らなくていい。ただ『名簿担当者（Service）』から情報を貰えばいい。この役割分担こそが、プロが作る『変更に強い設計』なんだ。」

## 6. まとめ：研修生に伝えたいメッセージ
> 「優れたエンジニアは、同じことを何度も書かない。フレームワークの仕組みを正しく設定することで、100の扉を一度に守ることができるんだ。Controller のコードから『ログインチェック』を追い出し、純粋な業務ロジックだけにする。このスッキリした美しさを感じてほしい。」

## 変更箇所の差分（修正前 → 修正後）

### `WebSecurityConfig.java`

**修正前**（未設定 or 不十分）— 直 URL で `/employee/showList` にアクセス可能

**修正後**（抜粋）

```java
http.authorizeHttpRequests(auth -> auth
    .requestMatchers("/", "/insert", "/toInsert", "/login").permitAll()
    .requestMatchers("/employee/**").authenticated()
    .anyRequest().authenticated()
)
.formLogin(login -> login
    .loginPage("/")
    .loginProcessingUrl("/login")
    .usernameParameter("mailAddress")
    .passwordParameter("password")
    .successHandler(loginSuccessHandler)
    .failureUrl("/?error=true")
);
```

### `LoginAdministratorDetailsService.java`（既存を利用）

```java
@Override
public UserDetails loadUserByUsername(String mailAddress) {
    Administrator admin = administratorRepository.findByMailAddress(mailAddress);
    if (admin == null) {
        throw new UsernameNotFoundException(...);
    }
    return new User(admin.getMailAddress(), admin.getPassword(), authorityList);
}
```

**修正前** — 独自 `@PostMapping("/login")` でセッション管理  
**修正後** — ログイン処理は Security に任せ、`/` はログイン画面表示のみ
